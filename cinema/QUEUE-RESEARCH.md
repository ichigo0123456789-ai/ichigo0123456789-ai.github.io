# 待機列（仮想待合室）調査と「最速で・正直に」取る戦略

調査日: **2026-08-20**（Web調査＋KINEZO公開ページ解析）。
方針の大前提: **列のスキップ・多重接続・トークン偽造・IP分散・CAPTCHA回避はしない。**
不正はBAN・規約違反・不公平を招く。ここでやるのは「**正直な単一接続で、列を含めて最短で通過して掴む**」正攻法のみ。

## 2. KINEZO（T・ジョイ）の実測

- 予約フロー `reservation/index → choice_seat` に **第三者待機列ベンダ（Queue-it等）も待機ページも無し**。
  ページ内の `queueTime` は **New Relic の計測タグ**で待機列とは無関係。
- サーバは Apache/PHP、**CloudFront** 配下。`meta refresh` 無し。
- 発売前日付は番組表APIが**0件**を返す（＝予約URLは発売枠に入ってから出現）。
- 結論: **通常は待機室なしの直接アクセス方式**。ただし高需要の発売時のみ動的に
  「混雑」画面が差し込まれる可能性は残るため、コード側で**検出して正直に待つ**（§4）。

## 3. 「列がある/混む」ときに最速で取る、正攻法の優先順位

**① 会員先行を使う（最大の合法的アドバンテージ）**
TOHO/109/イオン/ユナイテッドは会員が数時間〜1日早く買える。**先行枠で買えば一般0時の
一斉アクセス自体を回避**できる。人気作を頻繁に取るなら各チェーンの会員登録は必須。
（T・ジョイKINEZOは先行枠が無いので0時の速度勝負になる。）

**② 発売前に「準備」を完了しておく（各社公式の推奨）**
- 事前ログイン、会員情報・**支払い方法の登録を済ませておく**。
- 本ツールは発売前に：ログイン → セッション維持 → **接続ウォームアップ** → サーバ時刻同期、を実施済み。
  ＝公式が言う「準備」を自動でやっている状態。

**③ T=0で単一接続・最短で掴む**
本ツールの `choiceSeatSave` 直POST（サブ秒）。列が無い/FIFO型なら速度がそのまま効く。

**④ 待機列が出たら、正直に待って解放と同時に掴む（§4）**
多重接続や列スキップはしない。単一接続で、システムが示す間隔で順番を待ち、
座席画面に解放された瞬間に掴む。

## 4. 待機列で速度が「効く／効かない」の見極め

待機列には2型ある：
- **(a) 事前ロビー＋抽選型**: T=0時点で待合室に居た人を**ランダムに整列**。早い者勝ちにならず、
  **速度は無意味**（速度対策の仕組み）。この型では「先行枠を使う」「そもそも並ぶ」以外に手はない。
- **(b) 時刻FIFO/スループット制限型**: T=0以降に処理され、**準備済み＆速い方が有利**。
  109の「0:00→0:02で席が埋まる」はこの型に近い（最初の解放波に乗れるかが勝負）。

→ **(b)型では本ツールの準備＋速度が効く。(a)型では効かない**（ここが速度改善の天井）。
どちらかは実際の発売を観測しないと確定できないため、ツールは**正直に待つ実装**にとどめ、
不正な追い越しはしない。

## 5. 実装（KINEZO向け・§4の(b)を正直に速く）

`runner` は openShow 後に**画面種別を判定**して分岐する（`Kinezo.pageKind`）：
- `seat`（choice_seat到達）→ 即 `secure()` で掴む。
- `waiting`（「しばらくお待ち/順番/混雑/アクセスが集中」や meta refresh）→
  **単一接続でmeta refresh間隔（無ければ既定2秒）で正直に再取得**し、解放されたら掴む。
- `notonsale`（販売期間外/発売前）→ 短間隔で再試行（発売枠入りを待つ）。
- `login`（セッション切れ）→ 1回だけ再ログインして再試行。
- `captcha` / `unknown`（想定外）→ **即停止して人間に引き継ぐ**（RULES.mdの原則）。

多重接続はしない。総待機に上限（既定10分）。進捗はログに出す。

## 6. 未確認・正直な限界

- KINEZO高需要時に実際どんな待機画面が出るか（出るのか）は未観測。§5の`waiting`判定は
  キーワードベースの**ベストエフォート**で、実際の文言に合わせて後で調整が要る可能性。
- (a)抽選型かどうかは各社とも公表しておらず不明。抽選型なら速度は効かない。
- **結局いちばん効くのは「会員先行を使う」こと**（KINEZO以外）。技術的速度は先行枠に勝てない。
