# 座席オートリザーブ — T・ジョイ横浜

T・ジョイ横浜（予約システムは **KINEZO**）の上映回と座席の優先順位を
**あらかじめ決めておき、発売開始と同時に座席を確保する**ためのツール。

公開先: `/cinema/`

---

## 現状（Phase 1）

**KINEZO へは一切アクセスしません。** GitHub Pages は静的サイトで、
ログイン・座席クリック・決済といった操作を行う実行体を持てないためです。

Phase 1 では代わりに「他ユーザーが席を埋めていく劇場」をブラウザ内で再現し、
その上で確保ロジックを検証します。

### できること

- 上映回の指定（シアター / 作品 / 上映日時 / 枚数 / 券種）
- 発売開始日時の設定（KINEZO の「鑑賞日の2日前 0:00」からの自動計算つき）
- **シアターごとの座席表からの座席選択**（連席選択・中央の見やすい席の自動選択）
- 発売開始までのカウントダウン
- 確保ループの実行（事前接続 → 待機列 → 発売の瞬間に確保 → 取れなければ再試行）
- サーバ時刻との同期、発売時刻ちょうどでの発火
- 実行ログ・座席状況・所要時間の内訳の表示
- 確保後の Google カレンダー登録 / `.ics` ダウンロード
- プランの保存（この端末の localStorage のみ）

### まだやっていないこと

- 座席の優先順位付け（第2候補・第3候補）— 後回しにしている
- 実サイトへのアクセス、ログイン、実際の座席確保
- 決済（Phase 2 で追加）
- 複数アカウントでの並列実行、同一上映回の多重確保（意図的に対応しない）

## ファイル構成

| ファイル | 役割 |
|---|---|
| `index.html` / `style.css` | 画面 |
| `app.js` | UI・プラン編集・座席の優先順位付け・カレンダー連携 |
| `runner.js` | **確保ループ本体**（チェーン非依存） |
| `speed.js` | 時刻同期・高精度タイマー・計測 |
| `engine.js` | 座席バックエンドの**アダプタ境界**と、Phase 1 用のモック実装 |
| `data/theaters.js` | T・ジョイ横浜の9シアターと座席レイアウト |

### アダプタ境界

`runner.js` は次の4メソッドにしか依存していません。ここが Phase 2（KINEZO 対応）との接合点です。

```js
open(ctx)               -> { ok, queueSec }              // 座席選択画面を開く
fetchSeatMap(ctx)       -> { ok, seats: {[id]: state} }  // 座席状況を取る
hold(ctx, seatIds)      -> { ok, holdExpiresAt } | { ok:false, reason }
release(ctx, seatIds)   -> { ok }
```

`state` は `available` / `taken` / `blocked` / `mine`。車椅子スペースは常に `blocked`。
`ctx` は `{ now, onSaleAt }` で、時計は呼び出し側（`CinemaRunner.Clock`）が持ちます。
早送りのリハーサルと本番実行が同じコードを通るのはこのためです。

- 列ごとの内訳（左 / 中央 / 右）:

  | B | 2 | 15 | 2 | 19 | |
  | C・D | 4 | 15 | 4 | 23 | |
  | F〜I | 4 | 15 | 4 | 23 | F列の手前が横通路 |

  | K | 0 | 15 | 4 | 19 | 左ブロックが無い |

  合計 325席。車椅子スペースは J・M の各1つで計2つ（ID は `J-WC1` / `M-WC1`）。

**席番号だけは確認できていません。** 公式の座席表に番号が印字されておらず、

## 発売の瞬間の速さ

「速く取る」の中身はほぼ次の3つに分解できる。効く順に並べてある。

### 1. サーバ時刻とのズレを消す（`speed.js` / `TimeSync`）

手元の時計が2秒遅れていれば、どれだけ速いコードでも2秒出遅れる。体感で最も効くのはここ。

HTTP の `Date` ヘッダは秒精度しかないが、「オフセットが取りうる1秒幅の区間」が
毎回得られると考えれば、秒境界をまたぐようサンプルを散らして交差させることで
サブ秒まで絞り込める。

```
応答生成時のサーバ時刻 S ∈ [D, D+1000)      D = Date ヘッダ
応答生成時のローカル時刻 ≈ t0 + rtt/2
offset = S - (t0 + rtt/2) ∈ [D - t0 - rtt/2,  D + 1000 - t0 - rtt/2)
```

12サンプルで実測 ±35ms 程度まで収束する。Phase 2 のローカル runner では
KINEZO のレスポンスヘッダから同じ方法で測る。

### 2. 発売時刻ちょうどに発火する（`speed.js` / `PreciseTimer`）

`setTimeout` は数十ms〜数百msずれる。遠いうちは `setTimeout` で粗く寄せ、
最後の60msは `MessageChannel` で詰める（`setTimeout(…, 0)` の 4ms クランプを受けず、
ビジーループと違ってメインスレッドも占有しない）。

実測で **発売時刻から +2〜3ms** に発火する。

なお背景タブではブラウザがタイマーを1秒以上まとめるため、この精度は出ない。
消せない制約なので、`VisibilityWatch` で検出して警告する。

### 3. 発売の瞬間の往復を1回減らす（`runner.js` / `holdFirst`）

座席表を取ってから確保すると、確保が1往復ぶん遅れる。欲しい席が決まっているなら、
いきなり確保を投げたほうが速い。失敗して初めて座席表を取りにいく。

モック環境での実測（シアター4・混雑「激戦」・16シード）:

| | 確保成功 | 平均所要 |
|---|---|---|
| `holdFirst` 有効 | 8/16 | 231ms |
| `holdFirst` 無効 | 5/16 | 535ms |

ただし**事前接続で待機列を抜けてから発売時刻を迎えている場合に限る**。
事前接続が足りず待機列を発売後に通過する設定では、往復1回ぶんの差は
結果を変えなかった（下記「測って示す」参照）。

発売から5秒以上経ってから始めた場合は、目当ての席が埋まっていて空振りする往復のほうが
高くつくため、自動的に無効になる。

### 測って示す

速くなったと言い張らず、実行のたびにどこに何msかかったかを画面に出す。

```
事前接続 開始        -2,996 ms    —
事前接続 完了        -2,869 ms    127 ms
発売開始             +3 ms      2,872 ms
確保リクエスト送信    +3 ms          0 ms   ← 座席表を挟まないので発火と同時
確保レスポンス受信   +171 ms        168 ms
```

この表を見ると、**支配的なのは待機列と事前接続であって、最後の1往復ではない**ことが分かる。
事前接続の既定値を20秒前にしてあるのはそのため。

## 安全側に倒してある点

| 制約 | 値 | 理由 |
|---|---|---|
| 再試行間隔の下限 | 500ms | 連打はサーバ負荷になり、遮断されて成功率も下がる |
| 1実行あたりのリクエスト上限 | 400回 | 暴走時の歯止め |
| 打ち切り時間 | 既定180秒（UIで変更可） | 取れないときに粘り続けない |
| 発売直後の再試行 | 200ms間隔・5回まで | 時計のズレで撃つのが早すぎたときだけ。人が数回リロードする程度に収める |

`runner.js` の `MIN_POLL_MS` は UI から上書きできません。設定値がこれを下回る場合は
切り上げたうえでログに残します。

## Phase 2 の計画（実サイト対応）

静的サイトは**プランを組む場所**のままにし、実際の予約は手元PCで動く runner が担当します。

```
[GitHub Pages]                    [手元PC]
 プラン編集UI  --- plan.json --->  runner (Node + Playwright)
                                    ├ KINEZO アダプタ
                                    ├ OSキーチェーン（キネパス会員ID・パスワード）
                                    └ 確保 → 決済 → カレンダー登録
```

1. **KINEZO アダプタの実装** — `engine.js` と同じ4メソッドを Playwright で実装する。
   座席選択画面のDOMはサイト改修で壊れるので、セレクタは1ファイルに集約しておく。
   実座席表を取れるようになった時点で、`data/theaters.js` の残りの生成レイアウトと、
   シアター4の未確認の席番号を実 ID に置き換える。
2. **プランの受け渡し** — UI から `plan.json` を書き出し、runner が読む。
   UI 側は認証情報を一切持たない。
3. **決済** — 確保後に決済フォームを自動入力。誤購入を避けるため、
   金額と座席の確認ステップを必ず挟み、ドライラン（送信直前で止める）モードを用意する。
4. **時刻同期の相手を KINEZO にする** — いまは同一オリジン（このページ自身）の
   `Date` ヘッダで測っている。runner なら KINEZO のレスポンスから直接測れる。
5. **座席の優先順位** — 第2候補・第3候補への自動フォールバック。いまは後回しにしている。
6. **カレンダー登録** — 購入完了を検知してから予定を作る。
   確保しただけの段階で予定を入れない（決済に失敗すると嘘の予定が残るため）。

## 個人情報の扱い

| データ | 保存先 | 外部送信 |
|---|---|---|
| 予約プラン | この端末の localStorage | なし |
| 実行ログ | メモリのみ | なし |
| 予約者情報（氏名・電話・メール） | 設定を ON にしたときのみ localStorage | なし |
| キネパス会員ID・パスワード | Phase 1 では扱わない | — |
| クレジットカード情報 | Phase 1 では扱わない | — |

Phase 2 で認証情報が必要になった際の方針:

- ブラウザ側には置かず、手元PCの runner だけが持つ
- OS のキーチェーン（macOS Keychain / Windows 資格情報マネージャー / libsecret）に保存し、平文の設定ファイルには書かない
- 認証情報を含むファイルは `.gitignore` で除外する
- ログ出力時に会員番号・カード番号をマスクする

## 使ううえでの前提

- KINEZO の利用規約で自動アクセスが禁止されている場合があります。使う前に必ず規約を確認してください。
- このツールは**自分が観る1件の予約**を取ることだけを想定しています。転売目的の大量確保はできない作りです。
- シアター4の座席配置は公式の座席表から起こした実データですが、**席番号は未確認**です。
  シアター4以外は**列ごとの座席配置も近似**です（上記「劇場データ」参照）。
- 料金や発売ルールは改定されます。実際に使う前に公式サイトで確認してください。
